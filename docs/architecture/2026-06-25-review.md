# Architecture Review — 2026-06-25

> Forward-looking review of usability, expense mgmt, corpus, dues, reporting, calculations, and cross-cutting concerns. Builds on the same-day auditor review at `docs/audits/2026-06-25-auditor-review.md`.

## TL;DR

The app is **statutory-grade today** for Lilac Apartments. Dues math has zero drift between view and recomputed values across 44 flats, AGM bundle ships all four canonical reports, RBAC is real, audit triggers cover critical tables, owner portal is genuinely useful. The 2026-06-23 + 2026-06-25 fixes closed the structural balance-mismatch class.

**To future-proof for the next 2 years, three structural investments matter most:**

1. **Single calc primitives layer** (DB views + RPCs) so Dashboard, Balance Sheet, R&P, and Owner Statement all read the same numbers. Three of those today reduce CR−DR independently from the `transactions` table.
2. **Canonical TypeScript types + DB integrity constraints** so silent drift becomes structurally impossible (header vs Σ line items, voucher gaps after rollback, FD-interest dual sources).
3. **Real announcements + notifications layer + owner power-pack** (UPI deeplink + AGM download). The current `app_settings` JSON blob can't grow; the owner portal already has the right primitives but not the action surfaces.

Everything else is iteration on these three foundations.

---

## Method

Three-track review:
- Auditor data review (already done — `docs/audits/2026-06-25-auditor-review.md`)
- Two parallel agent deep-dives (expense management; reporting + dashboard + owner portal) with concrete file:line references
- Direct review of layout/nav/RBAC/dues/corpus/calc views

Per-area findings are grouped **Strengths / Gaps & Risks / Forward-looking opportunities**, then consolidated into a phased roadmap.

## 1. Calculations & the ledger

### Strengths
- `transactions` is a single, audit-logged source of truth. `row_type IN ('Normal','VOIDED','SPLIT')` plus `split_refs` cover void and split flows cleanly.
- `v_dues_tracker` matches recomputed-from-raw values to the rupee (44 flats, zero drift) — verified today.
- `v_corpus_tracker` handles multi-plan correctly via `plan_id` + FY-range fallback; today all 65 corpus CRs carry `plan_id` after the audit backfill.
- Maintenance rate history is forward-only with `effective_from`/`effective_to` — handles mid-year rate changes per flat.
- Opening balance is a real `Normal` CR transaction row, not a settings key — audit-friendly.

### Gaps & Risks
- **Calc duplication across surfaces.** Balance Sheet bank balance (`ReportPage.tsx:2034`), Dashboard "Net Available Cash" (`DashboardPage.tsx:222`), and R&P opening (`ReportPage.tsx:1762`) each independently reduce CR−DR from `transactions`. Three sites = three places to forget the `.neq('row_type','VOIDED')` filter again. This was the round-1 root cause of the balance mismatch.
- **FD interest dual sources.** R&P reads FD interest from `deposits.maturity_amount − principal` when matured; the audit fix put real quarterly interest credits in `transactions` with `category='FD Interest'`. These can disagree.
- **Magic constant `44 flats`** lives in `ReportPage.tsx:219` AND the Excel export string. Should derive from `(SELECT COUNT(*) FROM flats)`.
- **No double-entry semantics.** Single-ledger means a "transfer" (e.g. cash → bank, or savings → FD) needs a workaround. Today `category='FD'` is used as a marker but there's no symmetric DR/CR pair.
- **Pseudo flat_codes** (`INTEREST`, `FD`, `EB`, `SEWAGE`, `SALARY`) overload the `flat_code` column. Types in `src/lib/supabase.ts` don't distinguish "real flat" vs "sentinel".
- **Per-month allocation isn't materialised.** "Months covered" is `floor(collected / monthly_rate)` client-side — works but can't answer "which months are paid?" or "did April get fully paid?". Important once a flat carries arrears across rate changes.
- **Legacy unused tables.** `maintenance_payments` and `corpus_payments` declared in old migrations are empty — drop them or document the choice.

### Forward-looking opportunities
- A small **`v_bank_balance_as_of(date)` view** + `rpc_fy_receipts(year)` / `rpc_fy_payments(year)` / `rpc_fd_interest(year)` set kills the duplication problem permanently. Every surface — Dashboard, Balance Sheet, R&P, Owner Statement — calls the same primitive.
- **`v_flats_summary`** (count, by block, by type) so `44` is derived everywhere.
- **A `transfers` table or sentinel category convention** that's first-class, not overloaded on `flat_code`. Could be as simple as `transactions.transfer_pair_id` for the DR/CR pair.
- **Per-month allocation table** `dues_allocations(flat_id, fy, month, allocated_amount, transaction_id)`. Source of truth becomes "which months are paid" not "how much was collected". Enables future receipts-style PDFs.

## 2. Expense management

### Strengths
- Clean header/line-item separation (`expenses` + `expense_line_items` in `006_expenses.sql:102-165`) with `cost_center` on the **line** (not header) — enables proper per-block allocation.
- **Concurrency-safe voucher numbering** — per-FY counter with `ON CONFLICT … RETURNING` (`006_expenses.sql:77-99`). Auditor review confirms zero duplicates / gaps.
- **Bidirectional reconciliation**: both `expenses.transaction_id` and `transactions.expense_id` are kept (`ExpensesPage.tsx:1330-1337`).
- **`bundle_pending_items` RPC** (`032_pending_line_items.sql:68-163`) is the best-written piece in the codebase — SECURITY DEFINER, role check, TOCTOU guard via re-asserted `voided_at IS NULL` + row-count comparison.
- **Soft-delete consistent** — `voided_at`/`voided_by`/`void_reason` on expenses + `pending_line_items`; `is_active` flags on `vendors` + `expense_categories` preserve FK history.
- **Approval workflow plumbing exists** — `approval_status`, `approved_by` (FK to `auth.users`), `rejection_reason`, partial index on pending.

### Gaps & Risks
- **No CHECK constraint enforcing `Σ line_items.amount = expenses.amount`.** Audit found zero drift today only because the UI keeps them in sync; any direct SQL edit can break it silently.
- **No line-item-level reconciliation.** A bundled expense covering 8 UPI line items gets matched to ONE aggregated bank row — you can't ever reconcile individual UPI lines back to their own bank DRs.
- **`approval_status` defaults to `'approved'`** (`031_approval.sql:13`) — backfill convenience that means any code path inserting without explicit `'pending'` skips approval entirely.
- **Audit triggers missing on `expense_line_items` and `expense_attachments`.** Editing a line-item amount or cost-centre isn't captured.
- **Voucher allocated `BEFORE INSERT`** — if the insert rolls back, the counter has already incremented in the separate counter table. Produces gap-free numbering as long as inserts succeed; failed inserts leave holes.
- **`expense_attachments.file_url` is plain text** — no MIME type, no checksum, no version. Re-uploading the same receipt silently shadows.
- **`src/lib/supabase.ts` lacks canonical `Expense`, `ExpenseLineItem`, `Vendor`, `Staff` interfaces.** Each page (notably `ExpensesPage.tsx:31-91`) redefines them locally with slightly different field sets — single schema change = N call-site edits.
- **Unpaginated DayBook** (`ExpensesPage.tsx:218-230`) — fine at 68 rows, slow at 500–1000 with embedded line items.

### Forward-looking opportunities
- **Header-vs-line deferred trigger** that recomputes Σ and either updates or rejects the header.
- **`expense_budgets(fy, category_id, amount)` + `v_budget_vs_actual`** — converts the subsystem from bookkeeping to governance.
- **Approval thresholds** in `app_settings`: `auto_approve_below`, `committee_required_above`, `agm_required_above`. The infrastructure (status enum, rejection_reason) is already in place.
- **TDS / GST tracking on vendor payments** — `pan_number` validation, `tds_rate`, `tds_amount`, `gst_number` on `vendors`/`expense_line_items`. Lilac doesn't need it today but anything paying >₹30k/year to a contractor legally does.
- **Receipt OCR** — Supabase Edge Function calling Claude/Gemini vision on upload, writing parsed fields to `expense_attachment_extractions`. One-click "create expense from receipt".
- **Auto-categorisation rules** — `description_pattern → category_id` table mirroring the transaction tagger.
- **Vendor scorecard** view — `count, total_paid, avg_days_to_pay, dispute_count`.
- **Recurring template → cron-generated pending items** monthly.

## 3. Corpus collection

### Strengths
- Multi-plan model with **per-flat targets** (`corpus_plan_flats.target_amount`), **carry-forward** between plans (`carry_forward_amount`, `carry_forward_plan_id`), and **flexible installment schedules** (`corpus_plan_installments` + per-flat amounts).
- Lifecycle: `draft → active → completed → cancelled` with `closed_at` + `close_notes`.
- **Overlap detection at activation** via `get_overlapping_active_plans()` (migration 029).
- WhatsApp broadcast + per-flat reminder both functional with copy + send (auto-prefix country code when phone on file).
- "How your corpus is used" on owner portal — categorised corpus expense breakdown per plan. Rare and excellent.

### Gaps & Risks
- **FY-range fallback in `v_corpus_tracker`** (migration 025) silently double-counts if 2+ plans' FY ranges overlap AND `plan_id IS NULL` on any rows. Backfill closed today's exposure but **upload-time validation isn't enforced** — a future import without `plan_id` re-opens it.
- **Carry-forward semantics are implicit.** `carry_forward_amount` adds to target on the new plan; no audit trail showing "this amount came from plan X's residual".
- **Installment workflow exists in schema but isn't surfaced** in v_corpus_tracker — it tracks plan-level collected/balance but doesn't compute "installment 2 is overdue".
- **`plan.total_target` vs Σ(`plan_flats.target_amount`)** has no CHECK constraint — audit found zero drift today, but no structural guarantee.
- **No corpus burndown forecast.** With contributions trickling in, the team can't see "at current rate, plan closes in N months" or "Y flats projected to miss the FY-end target".

### Forward-looking opportunities
- **Require `plan_id` at upload time** for any `corpus='YES'` transaction.
- **Corpus burndown / pace view** — chart of cumulative collected vs target vs FY-end, with projection.
- **Installment-level tracking surfaced**: "installment 2 overdue for 3 flats" alert + per-flat installment table.
- **Carry-forward as a linked transaction** — when closing a plan with residual, generate a paired `transfer` row crediting the next plan.
- **Refund flow** for cancelled plans — `corpus_payments` → flat credit (today's `flat_credits` table is one path).

## 4. Dues management

### Strengths
- `v_dues_tracker.total_outstanding` correctly composes annual_due + arrears − collected − credits with zero drift.
- **Aging tabs** (Due / 30d+ / 60d+ / 90d+ / Partial / Clear) — well-chosen filter set; multiplied against `maintenance_amt` for threshold (`DuesPage.tsx:26`).
- **Carry-forward FY support** via `dues_start_fiscal_year` setting — track from a different start year than the current one.
- WhatsApp broadcast + per-flat reminders both functional.
- Arrears UI on Dues page lets admin record opening balances.

### Gaps & Risks
- **Aging thresholds are amount-based, not date-based.** "30d+" means `pending > maintenance_amt * 1` — actually a 1-month-rate threshold, not a date age. Confusing label.
- **Status derivation duplicated** — view computes it, page re-derives it (`DuesPage.tsx:104-109`). Should be one or the other.
- **Status in view is amount-based** (clear if collected ≥ annual_due) which ignores arrears + credits; UI does the right thing via `effectiveStatus`. View should expose `effective_status` itself.
- **No per-month allocation** (same gap as §1) — can't show "May not paid" cleanly.

### Forward-looking opportunities
- **`v_dues_tracker.effective_status`** computed once in SQL.
- **Per-month allocation** + month-grid UI (visual matrix of months × flats with paid/unpaid).
- **Dues forecast** — at current collection rate, when will pending clear?
- **Multi-FY view** — collection rate trend, arrears age distribution.
- **Late-fee policy** — settings-driven, auto-computed on `v_dues_tracker`.

## 5. Reporting & AGM

### Strengths
- **Statutory-grade AGM bundle** — Defaulters List, I&E, R&P, Corpus Fund Statement + standalone Balance Sheet (`ReportPage.tsx:454-752,1756,1960`).
- **PDFs lazy-loaded** via dynamic `@react-pdf/renderer` import — bundle stays small.
- **Dual-channel reminders** on flat statement (`buildConsolidatedReminder` at `ReportPage.tsx:901`) with WhatsApp deeplink + phone auto-prefix.
- Data sources consistently come from views (`v_dues_tracker`, `v_corpus_tracker`, `v_monthly_summary`, `v_monthly_collection`).

### Gaps & Risks
- **Calc duplication** (already in §1) — three Balance-Sheet-class queries in three files.
- **No Trial Balance** — for audit defensibility, even a category-level T-balance from `transactions` + `expenses` would be cheap.
- **No General Ledger CSV export** — auditors only see PDFs.
- **No prior-year comparatives** in I&E or Balance Sheet PDFs. AGM convention is "Current FY vs Last FY" side-by-side.
- **No budget vs actual** despite `expense_categories.budget_type` distinguishing Maintenance/Corpus.
- **`ReportPage.tsx` is 2,198 lines** — splitting per-tab will improve maintainability + lazy-load perf.

### Forward-looking opportunities
- **Auditor self-serve full-ledger CSV** export.
- **Prior-year comparatives** in all PDF reports.
- **Budget vs actual** — surface `budget_type` as a target column.
- **"As-of date" picker** on every report — not just FY.
- **Email-scheduled report delivery** (cron + send) for monthly committee digests.

## 6. Owner portal

### Strengths
- **`effectiveStatus`** (`OwnerPortalPage.tsx:410-413`) correctly distinguishes Clear / Arrears / Partial / Due using `total_outstanding` vs `pending` — handles credits and arrears correctly.
- "How your corpus is used" categorised expense breakdown per plan — rare transparency.
- PDF statement self-download already exists.

### Gaps & Risks
- **No UPI deeplink** — UPI ID is plain text (`OwnerPortalPage.tsx:699`). One `upi://pay?pa=...&am=...&tn=FlatXX-corpus` link converts 30 seconds of typing into one tap.
- **No complaint / service-request channel** — no way to flag a leak or AGM proposal.
- **No push or email notifications** — announcements live in `app_settings` JSON; owners see them only by opening the page.
- **RLS verification needed** — owner queries filter client-side by `flat_code` (`OwnerPortalPage.tsx:195-209`). If RLS on `transactions` / `v_dues_tracker` isn't strict, a tampered client could read any flat.
- **No e-AGM** — voting, agenda, minutes are absent.
- **AGM PDF download is admin-only** — owners can't pull their own AGM bundle.

### Forward-looking opportunities
- **UPI deeplink + dynamic QR** (qrcode.react, ~5kb) with prefilled amount from `dues.pending` / `corpus.balance`.
- **Service request / complaint module** (table + status + assigned-to).
- **AGM e-voting**: agenda → voting period → tallied results, all auditable.
- **Per-resident announcement read state** + comments + reactions.

## 7. Dashboard

### Strengths
- KPI tiles **are navigation buttons** — clicking "Overdue flats" jumps to filtered Dues page.
- **"Pending Actions"** rolls up overdue flats + unreconciled expenses + FDs maturing within 30 days into one number (`DashboardPage.tsx:230`).
- 12-month chart (`DashboardPage.tsx:417-438`).

### Gaps & Risks
- **No MoM / YoY trend** — only absolute values.
- **Alert strip is shallow** — covers overdue/unreconciled/FD-maturing but not pending corpus arrears, expired rate-change dates, vendors crossing TDS threshold, stale uncategorised CRs.
- **Few chart types** — one ComposedChart; no expenditure-mix donut, no collection-rate trend.
- **Calc duplication** (same as §1).

### Forward-looking opportunities
- Collection-rate **trend chart** (collected ÷ due, monthly).
- **Expenditure mix donut** by category.
- **Forecast tile** — "At current rate, FY-end balance will be ₹X".
- Alert strip extension to vendors / TDS thresholds / stale CRs.

## 8. Usability & cross-cutting

### Strengths
- Sidebar nav with role-aware filter + mobile bottom nav (4 items + More drawer).
- `OWNER_BLOCKED` route guard + redirect from `Layout.tsx:87`.
- Role badge in topbar; `useRoleCtx` exposes `canWrite`/`canApprove`/`isAdmin`/`isOwner`.
- **22-resource permission map** in `app_settings.role_permissions` with `usePermissions().can(resource)` accessor. Admin always wins. Defaults are merged so new resources auto-appear.
- Notification bell with auto-refreshing review-queue badge (30s polling).
- Floating context-aware Help button on every route.
- Avatar initials with hashed-hue background — small but nice.

### Gaps & Risks
- **No global search** — top search bar was removed in 702f28b (intentional). Becomes a gap once there are 5+ years of transactions.
- **No keyboard shortcuts** — `/` to search, `g d` to go to dues, etc. would help power users (the treasurer).
- **No onboarding flow** — first admin / first owner gets dropped into the app with no guided tour.
- **Notification surface is hardcoded** (`Layout.tsx:312-318`) — only two items; should be a notifications table.
- **No i18n** — single-language UI. Not urgent for Lilac, but a forward-looking risk if the platform multi-tenants.
- **No "What's new" / changelog** — users have no way to see what changed between deploys.

### Forward-looking opportunities
- **`Cmd+K` command palette** — single best UX upgrade. Quick jump to flat/voucher/transaction.
- **Notifications as a table** — `notifications(user_id, kind, payload, read_at)` + edge function fan-out.
- **"What's new" panel** — markdown changelog rendered on first visit after deploy.
- **Onboarding wizard** for first admin / new owner.

## 9. RBAC + audit

### Strengths
- 4 roles (admin / committee / auditor / owner); per-resource permission map; admin override.
- RLS in place per migration 013 + 020.
- Audit log via Postgres triggers on 7 tables (not app-level — survives bypass).

### Gaps & Risks
- **Audit log gaps** — `expense_line_items`, `expense_attachments`, `pending_line_items` (recently added) need trigger coverage check.
- **No row-level RLS verification suite** — when adding a new view/RPC, no automated check that owners can't read another flat.
- **`void_reason` not required** when voiding expenses — voidable without justification.
- **Permission map can be saved by anyone with `users.manage`** — no two-person confirmation for changes to RBAC itself.

### Forward-looking opportunities
- **RLS smoke tests** — Playwright suite that signs in as each role + tries forbidden actions.
- **Required `void_reason` + dual-approval for high-value voids**.
- **Audit-log download** for auditor role.
- **Permission-change audit** with optional two-person confirmation.

## Phased roadmap

Each phase ~2 weeks of effort for one engineer; ordered for compounding value.

### Phase 1 — Integrity foundations (highest ROI, lowest risk)
- DB-side primitives: `v_bank_balance_as_of`, `rpc_fy_receipts`, `rpc_fy_payments`, `rpc_fd_interest`, `v_flats_summary`.
- Replace the 3+ inline CR−DR aggregations with the new primitives.
- Header-vs-line CHECK trigger on expenses.
- Canonical types in `src/lib/supabase.ts` — `Expense`, `ExpenseLineItem`, `Vendor`, `Staff`, `Attachment`, `RecurringTemplate`.
- Audit triggers on `expense_line_items`, `expense_attachments`, `pending_line_items`.
- Drop legacy `maintenance_payments` / `corpus_payments` tables OR document why kept.
- Require `plan_id` at upload time for `corpus='YES'` rows.

### Phase 2 — Governance layer
- `expense_budgets` + `v_budget_vs_actual`.
- Approval thresholds in `app_settings`; auto-flip `approval_status`.
- Prior-year comparatives in I&E + Balance Sheet PDFs.
- Trial Balance + General Ledger CSV export.
- Required `void_reason` + dual-approval for high-value voids.

### Phase 3 — Owner power-pack (highest user-visible delta)
- UPI deeplink + dynamic QR on `/my-flat` with prefilled amount.
- Self-download AGM bundle from owner portal.
- Complaint / service-request module.
- Per-resident announcement read-state + comments.

### Phase 4 — Notifications + automation
- `notifications` table + Supabase Edge Function fan-out.
- Cron-driven recurring expense generation (uses existing `recurring_expense_templates`).
- Cron-driven monthly committee digest (email).
- Scheduled reminder fan-out (uses today's WhatsApp templates).

### Phase 5 — Intelligence layer
- Receipt OCR via Edge Function + Claude/Gemini vision.
- Auto-categorisation rules table.
- Corpus burndown forecast.
- Collection-rate trend + expenditure-mix donut on Dashboard.
- Vendor scorecard.

### Phase 6 — Platform-grade (only if multi-tenant becomes a goal)
- Multi-tenant schema (per-society isolation).
- e-AGM (agenda, voting, minutes).
- Per-month dues allocation table.
- i18n scaffolding.
- RLS smoke-test Playwright suite.
